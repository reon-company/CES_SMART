# 유지보수 주석 규약 (KO)

---

## 대상 독자 / 목표

| 항목 | 내용 |
|------|------|
| **대상 독자** | 신규 인수 개발자, 유지보수 담당자, 코드 리뷰어 |
| **목표** | 코드 변경 시 \"배경/의도/제약\"을 담은 주석을 작성하여 운영 리스크와 변경 포인트를 명확히 전달함 |

---

## 사전 준비물

- [ ] 프로젝트 소스 구조 이해 (`backend`, `frontend`, `arduino-r4`, `CES_CAMERA`)
- [ ] 기존 핵심 파일 1~2개 검토하여 주석 스타일 파악

---

## 1. 목표
- 주석은 코드 동작의 \"배경/의도/제약\"을 설명합니다.
- 구현 자체가 아니라 운영 리스크와 변경 포인트를 남깁니다.

## 2. 작성 원칙
- 왜 이 로직이 필요한가를 우선 설명
- 네트워크, 권한, 타임아웃, 재시도, 상태전이, 보안 제약 중심
- 하드웨어 연동 코드는 현장 장애 시 확인 포인트를 명시

## 3. 금지 패턴
- 코드 그대로 읽으면 알 수 있는 자명한 설명
- 과거 구현 기준으로 남아 있는 오래된 설명
- 주석과 실제 동작 불일치

## 4. 권장 패턴 예시
- BACKEND
  - `// Query token을 Authorization 헤더로 승격해 img 태그 스트림 요청도 인증 처리`
  - `// PNA/CORS 제약으로 프론트 직접 카메라 접근 대신 서버 프록시 경유`
- FRONTEND
  - `// 모바일에서 aspect-video와 min-height 조합 시 overflow 방지를 위해 w-full 강제`
  - `// 401 시 토큰 삭제 후 로그인 리다이렉트(무한 실패 루프 방지)`
- ARDUINO
  - `// WiFi 재연결은 loop 블로킹을 피하기 위해 상태기계로 분리`
  - `// MODULE_ID 불일치 시 서버에서 데이터가 다른 모듈로 귀속될 수 있음`
- ESP32-CAMERA
  - `// NVS 저장값이 없으면 fallback SSID를 사용해 현장 복구 가능성 확보`
  - `// /wifi/set 적용 후 즉시 재연결, 실패 시 serial 명령으로 수동 복구`

## 5. 적용 범위
- `backend/**/*.js`
- `frontend/**/*.js`, `frontend/public/**/*.html`
- `arduino-r4/**/*.{ino,h,cpp}`
- `CES_CAMERA/**/*.{ino,h,cpp}`

---

## 6. 단계별 주석 작성 절차

### Step 1: 변경 영향 구간 식별
- 네트워크 호출, DB 쿼리, 인증/권한, 하드웨어 연동 코드 우선 검토

### Step 2: "왜" 중심으로 작성
- 코드가 "무엇을" 하는지는 코드로 읽히므로 생략
- "왜 이 방식인지", "어떤 제약이 있는지", "변경 시 주의점" 위주로 작성

### Step 3: 검토 및 정리
- 자명한 설명 제거
- 오래된 주석은 실제 동작과 일치하는지 확인 후 수정 또는 삭제

---

## 7. 검증 방법 (정상/비정상 기준)

| 항목 | 정상 | 비정상 |
|------|------|--------|
| 주석 내용 | 배경/의도/제약 중 하나 이상 포함 | "i++" 같은 자명한 설명 |
| 일치성 | 주석과 실제 동작 일치 | 주석은 옛 로직, 코드는 변경됨 |
| 적용 범위 | 백엔드/프론트/하드웨어 핵심 로직 | 모든 라인에 과도한 주석 |

---

## 8. 자주 발생하는 문제와 해결

| 현상 | 해결 |
|------|------|
| 주석과 코드 불일치 | 코드 변경 시 해당 주석 동시 수정 또는 삭제 |
| 과도한 주석 | "무엇을" 하는 설명 삭제, "왜/제약"만 유지 |
| 영어/한국어 혼용 | 팀 규약에 맞춰 통일 (본 프로젝트: 한국어 권장) |
| 하드웨어 코드 주석 부재 | 현장 장애 시 확인 포인트(WiFi, 핀, NVS 등) 명시 |
